Why one rule per counterparty

Most spending goes to a small set of counterparties you pay again and again (the supermarket, the train, subscriptions), and new months mostly bring the same names. So one rule per counterparty is the right unit: a few dozen rules label most of a typical month. No pattern language or machine learning is needed for that.

How it works

A rule is one sentence"Counterparty contains albert heijn → Groceries." Optionally only for money going out (or in), or only on one account.
Rules only fill blanksThey never change a transaction that already has a category, and never touch transfers or members of a reimbursement group. Your own choices always win.
You can see every auto labelA label set by a rule remembers which rule. It shows a small "auto" mark, and the inspector says "Labelled by rule albert heijn → Groceries". Changing it by hand makes it yours.
Two moments to runOn import, for the new rows, inside the same database transaction. And once when you create a rule, for existing uncategorized rows, after showing how many it will label.

Where rules come from

  • From what you just did. After you categorize a transaction whose counterparty has more uncategorized rows, the inspector and the inbox offer: "Always label Albert Heijn as Groceries? 41 more will be labelled." One click creates the rule and applies it.
  • Suggested. When you pick the same category for the same counterparty twice in the inbox, the next card for that counterparty proposes the rule instead of asking again.
  • Starter rules (optional). Next to the starter categories: a short list of common Dutch merchants (Albert Heijn, Jumbo, Lidl, NS, Netflix, Spotify…) mapped to them. They'd label a good share of rows on day one.

Data model

One new table, and one nullable column that records which rule set a split. It replaces the "rules + category_manual flag" entry on the deferred list: a split with no rule is a manual one.

CREATE TYPE rule_direction AS ENUM ('out', 'in');

CREATE TABLE rules (
    id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    pattern      text NOT NULL CHECK (pattern <> '' AND pattern = lower(btrim(pattern))),
    category_id  bigint NOT NULL REFERENCES categories (id) ON DELETE CASCADE,
    direction    rule_direction,                                   -- NULL: money in and out
    account_id   bigint REFERENCES accounts (id) ON DELETE CASCADE, -- NULL: every account
    created_at   timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT rules_pattern_scope_key UNIQUE NULLS NOT DISTINCT (pattern, direction, account_id)
);

-- Which rule set this split. NULL = set by you (or a reimbursement default). Deleting a rule keeps its labels as manual.
ALTER TABLE transaction_splits ADD COLUMN rule_id bigint REFERENCES rules (id) ON DELETE SET NULL;

Matching: which rule wins

A transaction can match several rules. The longest pattern wins, because it's the more specific one; a rule limited to an account or a direction beats an equally long general one. Only one category is set, for the full amount.

Not in this proposal

  • Rules that split (e.g. 70% Groceries / 30% Household): rare, and a split is easy to do by hand.
  • Matching on description, IBAN or amount: the counterparty name already covers your recurring rows. Add a field when a real case needs it.
  • Regex or wildcards: substrings plus "longest wins" cover every example above.
  • Learned labels without rules (silently copying your last choice for a counterparty): hard to see why something got its label. The suggested-rule card gets the same benefit while you stay in control.

Decisions

  • Changing a rule's category moves the labels that rule set, and only those.
  • No generic starter rules. A suggested set of categories and rules built from your own exports replaces them.
  • The "Always label…" offer appears the first time you categorize a counterparty, whenever other unlabelled transactions match. In the inbox, press R to accept it.
  • The API exposes the rule on the transaction (Transaction.rule_id) rather than per split: rules always set one category for the full amount. The column stays on transaction_splits.
  • Transfer rules. A rule's target can also be a pot: "oranje spaarrekening → transfer to or from Savings", "broker → Investments". They run like category rules, record themselves in link_groups.rule_id, and only target pots: a rule never links two imported accounts, so the AMEX bill stays with the transfer suggestions. Offers after marking a transfer cover money in and out.
  • Amount ranges. A rule can be limited to amounts of at least and/or at most a size (inclusive; direction handles the sign), e.g. "tikkie, money out, up to 15 → Going out". A rule with a range is narrower, so it beats the same pattern without one, and one pattern can have several ranges.
  • Coverage preview. While writing or editing a rule, and when expanding one in the list, a scrollable list shows every match: will label, already labelled by this rule, or handled (categorized or linked, left alone).
  • Equal-length patterns (e.g. "ns groep" and "ah to go" in one name) fall back to the narrower scope, then the newest rule. A longer pattern settles it.
